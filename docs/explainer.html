01The shape of it

A private shared gym log for 3–10 friends. One feed, one weekly challenge, one weekly competition, and a currency you earn by training.

Three tiers, and the interesting thing is how thin the middle one is:

The one idea everything else follows from

Permissions are enforced in Postgres, not in application code. That single choice changes the failure mode of the most common mistake in a multi-tenant app:

Why it matters

A query missing its WHERE user_id = ? returns zero rows, not everybody's. The same slip that is a data breach in a conventional app is an empty screen here.

Why fra1 is in vercel.json

Vercel puts new projects in iad1 (Washington). Supabase is in Frankfurt. Left alone, every query crosses the Atlantic — roughly 100 ms each way, paid per query, on requests that make several. One config line removed the largest latency cost in the system before any code existed.

03Data model

Fourteen tables. The havura — the crew — is the tenant boundary, and almost every row is reachable only through membership in one.

Four decisions worth defending

a. The currency is a ledger, not a number

profiles.creatine_balance is a cache. creatine_ledger is the truth, append-only, with balance_after stamped on every row. One function — apply_creatine() — writes both, in one transaction, under SELECT … FOR UPDATE.

A single integer cannot answer "why do I have 825?". A ledger can, and it turns the invariant into a one-line test: cache == SUM(ledger).

b. Idempotency is an index, not code

create unique index creatine_ledger_ref_uniq
  on creatine_ledger (user_id, reason, ref_type, ref_id)
  where ref_id is not null;

A replayed Stripe webhook, a double-clicked Buy button and a re-run settlement all collide here and lose. The same trick on workouts (user_id, source, external_id) makes a future Hevy importer safe before it is written.

c. A composite foreign key enforcing a product rule

inventory carries item_kind, denormalised from shop_items, with a composite FK on (item_id, item_kind) so the two can never disagree. That makes this possible: 

create unique index on inventory (user_id, item_kind) where equipped;

"One equipped item per kind" is enforced by the database, not by whichever code path happened to call equip().

d. Views that cannot bypass RLS

The trap

A view runs as its owner by default — which is postgres — and therefore bypasses RLS on every table beneath it. A default-written view over workouts would serve every crew's sessions to anyone allowed to read the view. A total RLS bypass, introduced by adding a view, with no policy changed.

Both views carry with (security_invoker = on).

04The write path

The client has no INSERT privilege anywhere. Every write that touches more than one row happens inside a database function.

Three reasons it is shaped this way

  • Atomicity. "Create a crew" is two inserts; "log a workout" is a parent, N children and a score. PostgREST gives no transaction across separate calls.
  • Trust. user_id always comes from auth.uid(), so calling the RPC directly still cannot act as somebody else.
  • Invariants. The balance cache is writable by exactly one function, so it cannot drift.

Three clients, deliberately

admin.ts imports server-only and throws if it ever evaluates in a browser. Importing it into a Client Component would ship the service-role key to every visitor — the worst mistake available in this stack, so it is guarded twice.

05The score

0–100, measured against your own recent baseline — which is the only reason a shared leaderboard between a beginner and a veteran means anything.

work per set  =  reps × (weight + proxy)   proxy = 30 kg for bodyweight movements
volume      =  Σ work

Load    0–50 :  25 × min(volume ÷ median(volume), 2)
Density 0–30 :  15 × min(density ÷ median(density), 2)
Coverage 0–20 :  4 per distinct primary muscle, capped

Medians run over the athlete's previous eight sessions. A normal day lands near 50 for anyone; a brutal day near 90 for anyone. Measure kilograms instead and the beginner loses before they start, stops looking at the table, and leaves — which is why most apps simply skip group competition.

Detail that keeps parity

The median is percentile_cont, which interpolates: [10,20,30,40] is 25, not 20 or 30. Getting this wrong is the easiest way to make the SQL and the TypeScript disagree.

Why the formula exists twice

compute_workout_score() in plpgsql is authoritative — the score is never accepted from the client, so nobody can award themselves a 100. scoreWorkout() in TypeScript draws the live preview while a session is being entered, and makes the formula unit-testable, which plpgsql is not.

Duplication is the cost; drift is the risk. tests/domain.integration.test.ts pins the two against each other on seven fixtures, against the real database. Without it, editing one and not the other passes silently — and the number an athlete watches while entering a session is not the number they are given for it.

The honest approximation

The 30 kg bodyweight proxy is a stated limitation. A pull-up is not zero work, but we do not collect bodyweight, so every bodyweight rep is credited a flat nominal load. It is wrong for a calisthenics athlete and it is written down as wrong.

06Settlement

The only place in the product where creatine is created from nothing. It has to be exactly right, and exactly once.

Ranking and the tie rule

Standard competition ranking: two tied for first are both rank 1 and the next is rank 3. A tie pools the shares of the positions it occupies — two tied for first hold positions 1 and 2, so they split 0.7 + 0.2 evenly at 45% each. Without pooling, the alphabetically luckier one takes 70%.

Largest remainder

Payouts are whole numbers that sum to exactly the pot. Naive rounding either invents creatine or loses it. Tested against pots of 333, 1, 7, 999 and 1,000,000.

Weeks run Sunday to Saturday, in Asia/Jerusalem

Not hypothetical

22:00Z on Saturday is 01:00 Sunday in Israel — the start of a new week. Bucket that by the UTC date and the session pays into a competition that already settled. This exact bug shipped in the production HavuGym system, where a UTC-stored timestamp was read with a local hour and came out three hours wrong.

Settlement is lazy, and that is a stated trade

Weeks close when somebody opens /crew, not on a cron. Vercel Hobby has no scheduler, and adding an external one for a job that runs weekly per crew is a whole operational dependency for very little.

Correctness does not depend on timing — only freshness does. Three guards make repeat runs harmless: only status='open' weeks in the past are touched, challenge rewards gate on paid_at, and every payment carries a ref that the ledger's unique index rejects on replay.

07Security

Three independent layers. Section 09 describes the time one of them was wrong and the other two held.

1. GRANT      which tables and which columns are reachable at all
2. RLS        which rows out of those
3. FUNCTION   who may perform a compound operation in the first place

The recursion trap

The natural policy on havura_members is "you may read rows of a crew you belong to" — a query on havura_members from inside a policy on havura_members. Postgres detects the cycle and fails with 42P17 infinite recursion. 

create function public.is_havura_member(p_havura_id uuid)
returns boolean language sql
security definer                  -- runs as owner, so not subject to RLS itself
set search_path = public, pg_temp  -- caller cannot redefine `public`
stable as $$ … $$;

The pinned search_path is not decoration: without it a caller could create their own schema, push it onto the search path, and make a privileged function resolve to a table they control.

Column-level grants: two holes closed

The policy "update your own workout" is correct. The grant was not — a plain grant update on workouts covers every column, including score: 

-- would have worked
UPDATE workouts SET score = 100 WHERE id = <mine>;

The fix is not a better policy. It is a narrower privilege:

grant update (title, notes, performed_at, duration_min)
  on workouts to authenticated;

score simply has no UPDATE privilege. You may correct what you wrote down; you may not grade yourself. The same shape protects profiles.creatine_balance.

Not-found and not-permitted are the same answer

A workout in someone else's crew returns 404. A 403 would confirm that a session with that id exists somewhere. Likewise a failed login always says "email or password is incorrect" — distinguishing the two turns the form into an account-enumeration oracle.

Invite codes are capabilities

There is no SELECT path on invite_code at all. Joining goes through join_havura(), so a wrong code and a non-existent code are indistinguishable and crews cannot be enumerated.

08Money

Stripe Checkout in test mode. The riskiest endpoint in the app, and the one place where two delivery paths are safer than one.

The webhook is fully public

Stripe has no session with us. Without signature verification, anybody on the internet could POST "payment succeeded" and credit themselves. 

const payload = await request.text();   // RAW. mandatory.
event = stripe.webhooks.constructEvent(
  payload, signature, process.env.STRIPE_WEBHOOK_SECRET,
);
The subtle part

The body must be read as raw text. Parsing to JSON and re-serialising changes the bytes, and the signature then fails for every legitimate event — a bug that looks exactly like a misconfigured secret.

Two paths, one guarantee

Crediting happens both from the webhook (reliable, asynchronous, occasionally delayed or misconfigured) and from the success page the customer is redirected to (immediate, but only if they come back). Either alone ends with a paying customer holding nothing.

Both are safe only because crediting is idempotent: whichever arrives second collides with the ledger's unique ref index and is swallowed. That index is what makes it affordable to be enthusiastic about crediting rather than careful about it.

The amount never comes from the browser

The client sends a pack slug. The price is read server-side, and crediting only happens after Stripe itself reports payment_status === 'paid'. A tampered request can at worst buy a different advertised pack at that pack's real price.

Cosmetics only, on purpose

Creatine buys a title, a badge or a theme — never a scoring advantage. Someone who spends money cannot out-rank someone who trains harder. The moment they can, the leaderboard stops being credible, and the leaderboard is the product.

09A request, traced

One flow followed all the way down, because the seams are where the design actually lives. This is "log a workout", from the keystroke to the stored score.

1 · The draft lives in the browser, and only there

workout-logger.tsx is the only meaningful client state in the app, because a half-entered session genuinely does not exist on the server yet. 

const [entries, setEntries] = useState<DraftExercise[]>([]);

// A blank set inherits the previous one: sets repeat far more often than
// they change, which is the difference between four taps and sixteen.
const nextSet = (previous?: DraftSet): DraftSet => ({
  weightKg: previous?.weightKg ?? '',
  reps: previous?.reps ?? '',
});

2 · The preview runs the real formula

const preview = useMemo(() => {
  const sets = entries.flatMap((entry) =>
    entry.sets.filter((s) => s.reps !== '' && s.weightKg !== '').map((s) => ({
      reps: Number(s.reps),
      weightKg: Number(s.weightKg),
      equipment: entry.exercise.equipment,      // drives the bodyweight proxy
      musclePrimary: entry.exercise.muscle_primary,  // drives coverage
    })));
  if (sets.length === 0) return null;
  return scoreWorkout({ sets, durationMin: Math.max(Number(duration) || 1, 1), priors });
}, [entries, duration, priors]);

priors came from the server as a prop — eight { volume, durationMin } pairs, nothing sensitive — so the preview recomputes on every keystroke without a round trip to Frankfurt.

3 · The Server Action validates, and refuses to be trusted

export async function logWorkoutAction(
  _prev: ActionResult<string> | null,
  formData: FormData,
): Promise<ActionResult<string>> {
  // The sets arrive as a JSON string in a hidden field. Malformed JSON is a
  // message, not a 500.
  let sets: unknown = [];
  try { sets = JSON.parse(typeof rawSets === 'string' ? rawSets : '[]'); }
  catch { return actionError('Could not read the sets you entered.'); }

  const parsed = logWorkoutSchema.safeParse({ havuraId, title, notes, durationMin, performedAt, sets });
  if (!parsed.success) return actionError(..., fieldErrorsFrom(parsed.error.issues));
The line that matters

There is no score in this payload. The action cannot send one, because the RPC below does not accept one. The only thing a caller can influence is what was actually lifted.

4 · One RPC, one transaction

const { data, error } = await supabase.rpc('log_workout', {
  p_havura_id: parsed.data.havuraId,
  p_performed_at: parsed.data.performedAt,
  p_title: parsed.data.title,
  p_notes: parsed.data.notes ?? '',   // nullif(trim(...),'') inside stores NULL
  p_duration_min: parsed.data.durationMin,
  p_sets: parsed.data.sets.map((set) => ({ exercise_id: ..., set_index: ..., ... })),
});

Sent through the user's client, so the JWT travels with it and the function sees a real auth.uid():

create or replace function public.log_workout(...)
security definer set search_path = public, pg_temp as 51431
declare v_uid uuid := auth.uid();
begin
  if v_uid is null then raise exception 'UNAUTHENTICATED'; end if;
  if not public.is_havura_member(p_havura_id) then
     raise exception 'NOT_A_MEMBER'; end if;

  insert into public.workouts (user_id, ...) values (v_uid, ...) returning id into v_id;
  insert into public.workout_sets (...) select ... from jsonb_array_elements(p_sets);

  update public.workouts
     set score = public.compute_workout_score(v_id)   -- computed here, from stored rows
   where id = v_id;
end; 51431;
  • v_uid := auth.uid() — the user id is never a parameter, so no caller can log as somebody else even by invoking the RPC directly.
  • Parent, children and score commit together, or none of them do.
  • Whatever the client believed the score was is irrelevant by this point.

5 · The page re-renders from the database

revalidatePath('/feed');
revalidatePath('/crew');
return actionOk(data as string);

No client cache to reconcile: the Server Component simply runs again and reads the row that now exists. The redirect to /workouts/<id> then shows the stored score — which, if the two implementations agree, is the number the preview showed.

The other flow worth tracing: closing a week

await ensureActivityWeeks(havura.id);   // create weeks the crew trained in
await settleDueWeeks(havura.id);        // settle every finished one

Both run with the service role, because authenticated has no INSERT on challenges or competitions — a member must not be able to invent a challenge with a target of 1 and a reward of 100,000. They are only ever reached from server code that has already confirmed membership. 

const results = settleCompetition(entries, competition.pot_creatine);

for (const result of results.filter((r) => r.payout > 0)) {
  await admin.rpc('apply_creatine', {
    p_user_id: result.userId,
    p_delta: result.payout,
    p_reason: 'competition_payout',
    p_ref_type: 'competition',
    p_ref_id: competition.id,      // ← the idempotency key
  });
}

Two people opening the crew page at the same moment both compute the same payouts and both try to pay. The unique index on creatine_ledger (user_id, reason, ref_type, ref_id) means the second one loses. Exactly-once, guaranteed by an index rather than by a lock we remembered to take.

10How it is tested

136 tests in three tiers, split by what they can actually prove.

TierCountWhat it proves
Unit — Vitest95Pure domain logic and validation. No database, no clock, no network. Runs in ~0.25s.
Integration — Vitest35Against the real database. 22 of them are attacks.
End-to-end — Playwright6Against the deployed application.

Why the integration tests are not mocked

This is the single most important testing decision in the project. Mocking the Supabase client would have proved that our mock refuses. The claim that needs proving is that Postgres refuses — with real policies, real grants and a real JWT. So the tests create real users, sign in for real, and attack: 

it('a member cannot award themselves a score', async () => {
  const before = await admin().from('workouts').select('score').eq('id', aliceWorkout).single();

  await alice.client.from('workouts').update({ score: 100 }).eq('id', aliceWorkout);

  const after = await admin().from('workouts').select('score').eq('id', aliceWorkout).single();
  expect(after.data!.score).toBe(before.data!.score);   // unchanged
});

Note there is no expect(error).toBeTruthy(). PostgREST reports an update that matched no permitted column as a success with zero rows affected, so the test asserts the thing that actually matters: the value did not move.

The test that stops the two score implementations drifting

const workoutId = await logWorkout(athlete, crew, sets, { durationMin: duration });
const stored = await admin().from('workouts').select('score').eq('id', workoutId).single();
const expected = scoreWorkout({ sets: scoredSets, durationMin: duration, priors });

// Postgres numeric is exact; JavaScript is float64. A cent of tolerance is
// honest about that rather than pretending they are bit-identical.
expect(Math.abs(Number(stored!.score) - expected.score)).toBeLessThanOrEqual(0.01);

Seven fixtures, including a zero-load set, a five-minute session and 100-rep sets.

One deliberately positive permission test

Among twenty-two attacks sits a member CAN correct the title of their own workout. Without it, a suite where everything is blocked would pass while the application was completely broken. A security test suite needs at least one test that fails if you lock the doors too hard.

And a checker that keeps the documents honest

npm run db:verify

Twelve invariants, each one a claim the security document makes: RLS on every table, anon holding no privileges, no UPDATE on score or on creatine_balance, and the cached balance equalling the ledger sum. If a document says it, this asserts it.

The one worth repeating out loud

The wallet bug is the most instructive. The profiles policy deliberately exposes crewmates so the feed can show names — so an unfiltered select returned one row per crew member, .single() failed, and the balance silently fell back to zero, surfacing as "every shop item is unaffordable".

RLS narrows what you are allowed to see. It does not decide which row you meant.

The one that would have been worse to "fix" naively

Every foreign key pointing at profiles cascades on delete — except havuras.created_by, which defaulted to RESTRICT. Since profiles cascades from auth.users, deleting any member who had ever created a crew failed with Database error deleting user and a 500. The account could never be removed, which is a privacy problem as much as a data one.

Why CASCADE would have been the wrong repair

ON DELETE CASCADE makes the error go away and introduces a far worse bug: deleting the founder deletes the crew, and the crew's own cascade takes every member's workouts with it. One person closing their account would erase nine other people's training history.

SET NULL is the honest model. A crew is a shared object that outlives the account that happened to open it, and havura_members already holds the ownership that actually matters — and it cascades correctly.

The security control that failed

Migration 0002 revoked everything from anon and granted back deliberately. But ALL TABLES only covers what exists at that moment, and the views were created four migrations later in 0006. Supabase's default privileges granted them straight back to anon, silently undoing the posture.

It never became a leak, because security_invoker = on meant the caller's own rights on workouts were still checked — and anon has none: 

GET /rest/v1/workout_feed  (anon)
→ 401  42501 permission denied for table workouts

Two independent controls, one of them wrong, and the other held. That is the entire argument for defence in depth, and it is worth saying out loud rather than patching quietly. Fixed twice in 0008: revoke what was granted, and change the default so the next object added does not repeat it.

13Defending it

The questions most likely to come, and the honest answer to each.

Why not just use Hevy, or an ORM, or a normal API?

Hevy solves documentation. This solves returning. An ORM would hide the RLS policies and the RPCs, which are the substance of the design. And there is no internal API because Server Components read the database directly — there is no /api/feed to rate-limit, authenticate and get wrong.

What stops a user giving themselves a perfect score?

Three things. The score is computed by compute_workout_score() inside the same transaction that stores the sets, and is never accepted as a parameter. There is no INSERT policy on workouts at all. And authenticated holds no UPDATE privilege on the score column — that is a grant, not a policy, so no policy mistake can re-open it. Tested in tests/rls.integration.test.ts.

How do you know RLS actually works, rather than that you wrote it?

Twenty-two integration tests create real users, sign in for real, and attack. Each passes only when Postgres refuses. Mocking the client would have proved only that our mock refuses. One test deliberately asserts a permitted action succeeds — a suite where everything is blocked would pass while the app was broken.

Why is the score relative rather than absolute?

Because a crew mixes a beginner with a five-year lifter. A table measured in kilograms is one the beginner loses before starting, stops looking at, and leaves. Measuring each session against that athlete's own trailing median means both score near 50 on a normal day. It is what makes group competition possible at all.

What's the biggest performance problem in the app right now?

The feed view aggregates before LIMIT, so Postgres groups every workout in the crew to return twenty. Measured at 10.5 ms on 35 rows, and linear in crew history. The fix — denormalise set_count and volume at write time, where the score is already being computed — is known and deliberately not applied yet, because the data does not justify the migration. Measured, documented, dated.

What would you do with another week?

In order: denormalise the feed aggregates; move settlement to pg_cron; build the Hevy adapter against the official API — the ingestion boundary and its idempotency index already exist; add explicit rate limiting; and collect bodyweight so the 30 kg proxy can go.

Isn't paid currency pay-to-win?

It would be, so it is structurally prevented. shop_items.kind accepts only title, badge or theme. There is no purchasable item that touches a score or a ranking. The product rests on a real friend group trusting the table; the moment money moves the table, there is no product.

Who is the customer, if the app is free?

The users are crew members. The paying customer is the anchor — the most invested member, the one who started the crew. The wobbler never pays and never needs to: he is the retention that makes the anchor's crew worth paying for. The product monetises the strong user and spends it on the weak one.

What did you get wrong?

Five things, listed in section 09 with how each was found. The two that taught the most: a grant that was correct as a policy and wrong as a privilege, and .single() assuming one row while RLS was correctly returning several. Both were the same class of error — reasoning about intent instead of about what the database was actually asked.
