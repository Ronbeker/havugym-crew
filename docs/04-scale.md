# מסמך סקייל בסיסי — HavuGym Crew

> מכסה את סעיף 8 בבריף. כל המספרים כאן נמדדו על הפריסה החיה, לא הוערכו.

---

## 1. צורת העומס

לפני מספרים — הבנת הצורה, כי היא קובעת מה בכלל מסוכן.

**המוצר מחולק מטבעו לחבורות של 3–10 חברים.** אין שאילתה אחת שנוגעת בכל המשתמשים. כל קריאה מסוננת ל-tenant יחיד, בין אם הקוד ביקש זאת ובין אם RLS אכף זאת. משמעות מעשית: **המערכת מתרחבת אופקית לפי חבורות, לא לפי משתמשים.** אלף חבורות אינן אלף פעמים יותר קשות משאילתה על חבורה אחת — הן אלף שאילתות עצמאיות, כל אחת בגודל של חבורה.

| דפוס | תדירות | עלות |
|---|---|---|
| קריאת feed | הכי גבוהה | אגרגציה על אימוני חבורה |
| רישום אימון | ~3 בשבוע למשתמש | כתיבה בטרנזקציה + חישוב ציון |
| חיפוש תרגיל | כמה בכל רישום | חיפוש טקסט על 660 שורות |
| דף חבורה | יומית | אגרגציה שבועית + סגירה עצלה |
| סגירת שבוע | פעם בשבוע לחבורה | O(חברים) |

## 3. הבעיה האמיתית שהמדידה חשפה

**זה הממצא המרכזי של המסמך, והוא לא היה ידוע לפני שהרצתי EXPLAIN.**

ה-feed נקרא מ-view שמבצע `GROUP BY` כדי לחשב מספר סטים, נפח ורשימת שרירים לכל אימון. התוכנית מראה:

```
Sort (rows=21)
  └─ GroupAggregate (rows=35)     ← 35 = כל אימוני החבורה
```

ה-`LIMIT 21` **לא נדחף מתחת ל-GROUP BY.** Postgres מאגרג את **כל** אימוני החבורה ורק אחר כך ממיין וחותך. עם 35 אימונים זה 10ms. עם 10,000 אימונים בחבורה ותיקה, כל טעינת feed תעבוד על 10,000 שורות כדי להציג 20.

זה עומס **ליניארי בהיסטוריה של החבורה** על הפעולה הנפוצה ביותר במוצר — בדיוק הדפוס שנראה תקין בפיתוח ונשבר בשנה השנייה.

### 3.1 למה לא תיקנתי את זה עכשיו
התיקון ידוע ואינו קשה: לחשב `set_count` ו-`volume` **בזמן הכתיבה** ולשמור אותם על `workouts`. הכתיבה כבר מחשבת ציון באותה טרנזקציה, אז זו אותה עבודה במקום שכבר קיים, וה-feed הופך לסריקת אינדקס טהורה על `(havura_id, performed_at desc)` עם `LIMIT` שנדחף עד הסוף.

לא ביצעתי כי זו דנורמליזציה שדורשת backfill ומיגרציה נוספת, והנתונים הנוכחיים לא מצדיקים אותה. **זו החלטה מודעת עם תאריך תפוגה ידוע:** היא הופכת נחוצה סביב אלפי אימונים לחבורה. עדיף למדוד ולהצהיר מאשר לאופטם מראש דבר שאולי לא היה נשבר.

## 4. Pagination

ה-feed משתמש ב-**keyset**, לא ב-offset:

```ts
let query = supabase.from('workout_feed')
  .eq('havura_id', havuraId)
  .order('performed_at', { ascending: false })
  .limit(limit + 1);
if (before) query = query.lt('performed_at', before);
```

- `OFFSET 1000` מכריח את Postgres לייצר ולזרוק 1000 שורות. עמוד 50 עולה פי חמישים מעמוד 1.
- Keyset מקבל את המיקום כערך (`performed_at < cursor`) ומשתמש באינדקס ישירות. **עמוד 50 עולה כמו עמוד 1.**
- `limit + 1` — שורה אחת נוספת נמשכת רק כדי לדעת אם יש עוד עמוד, בלי `COUNT(*)` נפרד.

מגבלה ידועה: שני אימונים באותה שנייה בדיוק עלולים לגרום לדילוג בגבול עמוד. הפתרון הוא cursor מורכב `(performed_at, id)`. לא מומש — הסיכוי בחבורה של 10 אנשים זניח, אך זו הצדקה סטטיסטית, לא הוכחה.

## 5. אינדקסים

32 אינדקסים. אלה שנבחרו במכוון:

| אינדקס | למה |
|---|---|
| `workouts (havura_id, performed_at desc)` | ה-feed. הסדר תואם את ה-`ORDER BY` כדי לאפשר keyset |
| `workouts (user_id, performed_at desc)` | היסטוריה אישית ובייסליין הציון |
| `havura_members (user_id)` | ה-PK הוא `(havura_id, user_id)` ולכן לא משרת את החיפוש ההפוך. **זהו הנתיב החם ביותר במערכת** — כל policy עובר דרכו |
| `workout_sets (workout_id)` | שליפת סטים |
| `creatine_ledger (user_id, created_at desc)` | ה-ledger |
| `creatine_ledger (user_id, reason, ref_type, ref_id) WHERE ref_id is not null` | **חלקי.** אינו רק ביצועים — הוא מנגנון ה-idempotency |
| `workouts (user_id, source, external_id) WHERE external_id is not null` | חוסם ייבוא כפול |
| `inventory (user_id, item_kind) WHERE equipped` | אוכף "פריט מצויד אחד מכל סוג" |

**אינדקס שחסר, ביודעין:** `exercises.name` לחיפוש. `ilike '%bench%'` מייצר Seq Scan — נמדד 3.4ms על 660 שורות, ולא ישתנה, כי הקטלוג הוא **קבוע**. 660 שורות סטטיות אינן בעיית סקייל. אם הקטלוג יגדל לעשרות אלפים או ייפתח לתרגילים מותאמים, הפתרון הוא `pg_trgm` עם אינדקס GIN. תוספת אינדקס שלא נמדדה כנחוצה היא עלות כתיבה בלי תמורה.

## 7. הפרדת לקוח / שרת

```
Server Components  קוראים ישירות מ-Postgres. אין JSON ביניים, אין API להגן עליו
Server Actions     כותבים. ולידציה ולוגיקה עסקית לא ניתנות לעקיפה
Client Components  רק היכן שיש אינטראקטיביות אמיתית
```

היתרון הסקיילי אינו רק גודל bundle: **אין endpoint לקריאה בכלל.** אין `/api/feed` שצריך rate limiting, אימות ובדיקת הרשאות נפרדת. שטח התקיפה ושטח הביצועים קטנים באותה מידה.

## 8. עשרות עד מאות משתמשים

בטווח הזה — הטווח שהבריף שואל עליו — **המערכת לא תתקשה.**

| משאב | מצב |
|---|---|
| Postgres | 44 שורות בטבלה הגדולה. Supabase Free מספק 500MB; במדידה הנוכחית 500 אימונים למשתמש ל-200 משתמשים עדיין רחוקים מהגבול |
| חיבורים | Vercel functions דרך ה-pooler. אין חיבור לכל בקשה |
| Functions | fra1, אותו אזור כמו המסד |
| Bandwidth | דפים ב-RSC, בלי JSON כפול |

**החישוב:** 200 משתמשים × 3 אימונים בשבוע = 600 כתיבות בשבוע ≈ 3.6 כתיבות בשעה בשיא. קריאות: ~10 טעינות feed למשתמש ליום ≈ 2,000 ביום. במדידה של 10ms לשאילתה זה **20 שניות של עבודת מסד ביום**. הצוואר אינו המסד.

## 10. סגירת השבוע — המגבלה הארכיטקטונית הגדולה ביותר

**סגירת שבוע מתרחשת כשמישהו פותח את `/crew`.** אין cron.

### 10.1 למה כך
Vercel Hobby לא כולל cron מתוזמן; הוספת שירות תזמון חיצוני הייתה מוסיפה תלות תפעולית שלמה עבור פעולה שרצה פעם בשבוע לחבורה.

### 10.2 מה זה עולה
| השלכה | חומרה |
|---|---|
| חבורה שאיש לא פתח שלושה שבועות — שלושתם נסגרים ברגע שמישהו כן | **תזמון**, לא נכונות |
| הסוגר משלם את המחיר בזמן טעינה | 3 שבועות ≈ 3 סבבים של RPC |
| שתי טעינות במקביל עלולות לנסות לסגור יחד | **מוגן**: `.eq('status','open')` + אינדקס ה-idempotency ב-ledger. תשלום כפול בלתי אפשרי |

**הנכונות אינה תלויה בתזמון.** רק העדכניות. זו הייתה ההחלטה — ובכוונה תחילה בוצעה כך שהמעבר ל-cron יהיה שינוי של קריאה אחת, לא של הלוגיקה.

### 10.3 מה הייתי עושה בגרסה הבאה
Supabase `pg_cron` שקורא לאותה פונקציה בכל יום ראשון ב-00:30 שעון ישראל. הלוגיקה כבר idempotent, אז הפעלה כפולה — ידנית ומתוזמנת — אינה מזיקה.

## 12. מה היה משתנה באלף חבורות

| # | שינוי | למה |
|---|---|---|
| 1 | דנורמליזציה של סיכומי ה-feed | הבעיה מסעיף 3 הופכת דומיננטית |
| 2 | `pg_cron` לסגירה | הסגירה העצלה מפסיקה להיות סבירה |
| 3 | פרטישן של `workouts` לפי חודש | הטבלה הופכת לגדולה ביותר |
| 4 | Cache ל-feed | tenant מבודד → cache פשוט לביטול |
| 5 | Read replica | הקריאות עולות על הכתיבות בסדר גודל |
| 6 | Rate limiting מפורש | 660 שורות בקטלוג × חיפוש בכל הקלדה |
| 7 | ניטור אמיתי | היום יש `/api/health` בלבד |

**מה שלא היה משתנה:** מודל ההרשאות. RLS לפי tenant מתרחב טוב, כי הוא כבר מכריח כל שאילתה להיות מסוננת. זה בדיוק הדבר שהיה קשה להוסיף בדיעבד — ולכן הוא נבנה ראשון.
