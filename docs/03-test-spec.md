## 1. מה נחשב "המוצר עובד"

לפני רשימת הבדיקות צריך להגדיר את הטענה. המוצר עובד אם **כל חמש הטענות הבאות נכונות בו-זמנית**:

| # | טענה | אם היא נשברת |
|---|---|---|
| 1 | חבר רואה את החבורה שלו, ורק אותה | דליפת מידע בין קבוצות — כשל חמור |
| 2 | ציון האימון נקבע בשרת ומשקף את מה שהורם | הדירוג חסר משמעות, המוצר מת |
| 3 | קריאטין נוצר ונגרע רק דרך מסלול אחד, ופעם אחת | כלכלה שבורה; אפשר לייצר כסף |
| 4 | שבוע נסגר בדיוק פעם אחת, והקופה משולמת במלואה | תשלום כפול או חלקי |
| 5 | קלט לא תקין נדחה עם הודעה מובנת | חוויה גרועה או שורה מושחתת |

כל קבוצת בדיקות למטה קשורה לטענה מהטבלה הזו. בדיקה שלא משרתת אחת מהן לא נכתבה.

## 2. אסטרטגיה — שלוש רמות

| רמה | כלי | מה היא מוכיחה | כמות |
|---|---|---|---|
| **Unit** | Vitest | לוגיקה עסקית טהורה, כולל מקרי קצה | 77 |
| **Integration** | Vitest + מסד אמיתי | ש-**Postgres** מסרב, לא שאנחנו חושבים שהוא מסרב | 35 |
| **End-to-end** | Playwright | שהמסע השלם מחזיק בפריסה החיה | 6 |
| | | **סה"כ** | **118** |

### 2.1 למה בדיקות האינטגרציה לא ממוקקות
זו ההחלטה המרכזית במסמך. אפשר היה לדמות (mock) את ה-Supabase client ולבדוק ש"המשתמש לא מקבל נתונים". זה היה מוכיח **שה-mock שלנו מסרב** — כלומר, שכתבנו נכון את ההנחה שלנו. הטענה שצריך להוכיח היא ש-**Postgres** מסרב, על סמך policies אמיתיות, grants אמיתיים ו-JWT אמיתי. לכן הבדיקות האלה יוצרות משתמשים אמיתיים, מתחברות באמת, ותוקפות באמת.

### 2.2 למה הן מופרדות
`npm test` מריץ רק unit — מהיר, offline, דטרמיניסטי. `npm run test:integration` דורש הרשאות ורשת. הפרדה זו מונעת מהחבילה המהירה להפוך לאיטית ולשברירית.

## 6. בדיקות מסד נתונים — `tests/domain.integration.test.ts` (13)

### 6.1 זהות SQL ↔ TypeScript (7 מקרים)
סט בודד, אימון רגיל, אימון ארוך מאוד, אימון קצר מאוד, סט בעומס אפס, חזרות גבוהות, סינגלים כבדים.

לכל מקרה: רושמים אימון אמיתי, קוראים את הציון שהמסד חישב, ומשווים ל-`scoreWorkout()`. סובלנות 0.01 — Postgres numeric מדויק ו-JavaScript הוא float64; להתעקש על זהות סיביות זו הונאה עצמית.

**בלי הבדיקה הזו, עריכה של אחת הגרסאות ולא של השנייה עוברת בשקט,** והמספר שהמתאמן רואה בזמן הזנה אינו המספר שהוא מקבל.

### 6.2 אינווריאנטים של ה-ledger (4)
- אותו `ref_id` שלוש פעמים → זיכוי **אחד**
- ירידה מתחת לאפס → `INSUFFICIENT_CREATINE`
- `creatine_balance == SUM(ledger.delta)`
- `balance_after` בכל שורה שווה לסכום המצטבר — ה-ledger משחזר את עצמו

### 6.3 חנות (2)
קנייה כפולה → `ALREADY_OWNED`; קנייה בלי כיסוי נכשלת **ולא מעניקה כלום**.

## 9. מה שנמצא בזכות הבדיקות

ארבעה באגים אמיתיים, שלושה מהם מהרצת הבדיקות ואחד מהסתכלות באפליקציה החיה:

| # | הבאג | איך נמצא | למה הוא לא נראה קודם |
|---|---|---|---|
| 1 | `rpad(name, 2, '.')` קיצץ **כל** שם לשני תווים | הסתכלות ב-feed | 'Da' הוא שם חוקי במסד. נראה רק כשארבעה חשבונות הופיעו יחד |
| 2 | שבועות שאיש לא פתח בהם את האפליקציה מעולם לא נסגרו ולא שולמו | בדיקת ה-ledger אחרי seed | דורש היסטוריה של יותר משבוע |
| 3 | היתרה נקראה 0 כי `.single()` על `profiles` החזיר ארבע שורות (חברי החבורה) | הסתכלות בחנות | ה-policy עשה את עבודתו; הקוד הניח שורה אחת |
| 4 | `weekRangeUtc()` חישב היסט אפס | בדיקת יחידה | הפונקציה לא הייתה בשימוש; הבדיקה כתבה את הציפייה הנכונה |
| 5 | ה-views קיבלו הרשאה ל-`anon` | `npm run db:verify` | `REVOKE ALL ON ALL TABLES` חל רק על מה שקיים באותו רגע |

באג 3 הוא המאלף מכולם: **RLS מצמצם את מה שמותר לראות; הוא לא מחליט איזו שורה התכוונת אליה.**

## 10. הרצה

```bash
npm test              # 77 unit — מהיר, offline
npm run test:integration   # 35 מול המסד האמיתי
npm run test:e2e      # 6 מול הפריסה החיה
npm run db:verify     # 12 אינווריאנטים של הסכמה
npm run test:all      # הכול
```

`db:verify` אינה חבילת בדיקות אלא **בודקת שהמסמכים אומרים אמת**: היא מאמתת שRLS פעיל בכל טבלה, של-`anon` אין הרשאות, שאין UPDATE על `score` ועל `creatine_balance`, ושה-cache שווה ל-ledger. כל אחת מהן היא טענה שמופיעה במסמך האבטחה.
